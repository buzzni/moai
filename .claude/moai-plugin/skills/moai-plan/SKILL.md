# moai-plan

The host interviews the person, then a planning subagent drafts a grounded plan. The moai CLI never launches an agent.

1. Read `moai models --json` and `moai writing --json`. Compare the `plan` identifier case-insensitively: a name containing `fable` qualifies; a name containing `opus` qualifies only when `effort_plan` is `xhigh` or `max`. All other names fail. On failure stop before interviewing or creating anything; print one line naming the keys to change (`plan` and, when needed, `effort_plan`), recommending `fable` or `opus` with `effort_plan = "xhigh"`. Identify the source from `written`, then `repo`, else default; the user config overrides repository recommendations. Never substitute a model automatically.
2. Inspect the repository, tracker and wiki for what can be learned without asking. Use `AskUserQuestion` to complete the interview: goal and done state, scope and exclusions, acceptance, protected areas and settled design, milestone (including explicit consent to join a running release or a new version), deadline and start, priority, review focus and risks. Ask follow-ups until decisions are settled. Never invent a start or deadline. No answer means no deadline.
3. Create a unique task directory with `mktemp -d "<scratchpad>/plan.XXXXXXXX"` before an epic exists. Save the interview, including the person's answers verbatim, as `<plan dir>/interview.md`. Pass the absolute plan directory and interview path, root and `Writing:` detail to the subagent. Keep all drafts and combined bodies there, even after an epic is created; do not reuse the directory for another plan. Call `Agent(subagent_type: "general-purpose", model: <plan>, effort: <effort_plan>, description: "draft plan", prompt: <draft brief>)` with this brief. If `Agent` refuses the `plan` name (it takes only the names it can raise a subagent on), stop and tell the person which key to change, as in 1 — never substitute another model:

    Draft a plan from the interview record at <interview path> and the repository at <root>. Writing: <writing>. Work only in <plan dir>, the absolute task directory supplied by the caller; do not write to the tracker or change repository files.
    Read the request, its evidence and enough code and tracker context to ground the split. Write short titles and concrete, actionable bodies with file and function locations, constraints, acceptance tests and review focus. For detailed writing use, for the epic: why this bundle · the person's decisions · promises · order and the files it shares · review focus; for a development member: goal · context (files and lines, the precedent) · what is decided · steps · acceptance (which tests) · out of scope · order and the files it shares · role, adding where and how (files, functions, structures) · important contracts and pitfalls after `what is decided`. Name the epic review section `Review focus / 리뷰에서 볼 것` (choose the English or Korean heading). For brief writing give what, where and tests. Classify each member using the difficulty rubric and explain why. Do not ask the person questions.
    Keep the person's decisions and exclusions, storage, concurrency, path security and output contracts, numbers and budgets, member order and review focus. Give entry-point files and functions as navigation hints; line numbers, proposed signatures and types are hints, not contracts. Describe acceptance tests by the failure conditions they must catch, not exhaustive test function names. Under `acceptance (which tests)`, write those failure conditions; test names are optional navigation hints. Make example commands executable with configured column names, the first column, spaces and shell quoting; when unknown use a placeholder such as `<first column>`. Put shared files and order in the epic once; a member's `order and the files it shares` names only its own place and files and points to the epic — do not repeat file lists or explanations in every member.
    Write a plan file, an epic body file and one body file per member under <plan dir>. Preserve the mapping from each plan title to its body file. Return first `Model ran: anthropic/<your real model name>`, then `plan: <absolute file>`, `epic body: <absolute file>`, and for each member `<title> <low|medium|high> — <reason>; body: <absolute file>`. Return each unresolved decision as `gap: <what>`; do not ask the user.
    `low` — text, comments, a one-line fix; behaviour unchanged
    `medium` — a behaviour change inside one file, ringed by tests
    `high` — several files, the write path, concurrency, the storage format, hooks; hard to undo

4. Present the epic and member titles, difficulty and any `gap:` lines once. If gaps remain, ask only about those and resume the same `agentId` with the answers; the subagent never asks the person. Have that same subagent rewrite the plan and bodies to reflect the answers, removing superseded designs from the active text and collecting what was removed and why briefly in one history section at the end of the epic body. Keep drafts of removed members for the backlog: the subagent returns each as `removed: <title>; body: <absolute file>`. Present the revised plan and obtain approval before writing the tracker. The person decides whether to attach a running milestone; omit `--milestone` without explicit consent. Encode dates in the plan or use `--due` and `--start` only as answered.
5. After approval, park removed member drafts in the backlog. For each `removed:` line, pass its exact title as one argument and stream its body file with `-b -`; quote both for the shell, including any single quotes in the title. The host registers new work with `moai add --from <plan file> --body -` (stream the epic body), adding `--milestone <id>` only when approved. If the person approved a new milestone, create it after approval with `moai milestone add`, using only the agreed version and dates, then attach it. For a backlog use `moai backlog promote <id> --from <plan file>`; preserve its inherited milestone and body: combine the carried body and approved epic details into a scratch file, then replace the body with `moai edit <epic> -b - < <combined file>`. Apply an explicitly approved milestone and dates to the epic; do not override an inherited milestone without that approval. Map returned member IDs to titles and apply each body with `moai edit <member> -b - < <body file>`. Record `model: anthropic/<Model ran> (<highest difficulty> — plan: interview and detailed plan)` on the epic, using the actual model name without repeating the vendor. Do not pick up the work.
