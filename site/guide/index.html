How to use moai

Install

The installer downloads the release archive together with SHA256SUMS, and installs nothing whose checksum does not match. There is no option to turn this check off.

macOS · Linux

curl -fsSL https://raw.githubusercontent.com/buzzni/moai/main/install.sh | sh
  • It installs to ~/.local/bin. That directory has to be on your PATH for moai to run.
  • To install somewhere else or a specific version, add the options after -s --. 
    curl -fsSL https://raw.githubusercontent.com/buzzni/moai/main/install.sh \
  | sh -s -- --dir ~/bin --version v0.1.0

Windows

Download the script in PowerShell, then run it as a file.

Invoke-WebRequest -UseBasicParsing -OutFile install.ps1 https://raw.githubusercontent.com/buzzni/moai/main/install.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File install.ps1
  • It installs to %LOCALAPPDATA%\Programs\moai. Pick the directory with -Dir and the version with -Version.
  • The installer does not edit your PATH. When the directory is not on it, it says so in one line.
  • Piping it, as in irm … | iex, is not supported: the PowerShell window would close along with the script.
  • It runs as is on a clean PC without the Visual C++ redistributable.

Update

moai update

Replaces the moai you are running with the latest release. When a new version is out, the top of the moai tui screen says so too. Running the install line again also updates.

Supported platforms

Prebuilt binaries are published for Linux (x86_64), macOS (Apple Silicon) and Windows (x86_64 · ARM64). Anywhere else, build from source with cargo build --release.

Getting started

Run this once in the root of the project you want moai to track.

cd <project>
moai init

In a terminal, a setup screen comes up first. Each row has its default already picked. Enter initializes with what is picked, and Esc quits without changing anything.

Once that is done, open an agent session and ask for work in plain words as you always do. The agent reads the current board with moai status when the session starts, and creates and moves issues on its own.

tui and web

moai has two screens. Agents read and change the tracker file directly without opening either. Open whichever you like when you want to see how the work stands.

moai tui — in the terminal

moai tui

See the list, the kanban board, the Gantt, statistics and the wiki in your terminal. Press SPC g, then one key for the screen you want. The next time you run it, the list, kanban board or Gantt you were last on opens.

moai tui
  • The mouse works too — click rows, scroll, resize the panes. The full list of keys is in moai tui --help.
  • Press SPC n to write a thought straight into the backlog.

moai web — in the browser

moai web

See the list, the kanban board, the Gantt and the wiki on 127.0.0.1:6624. Open the browser yourself. Use it to share progress with teammates who are not at home in a terminal.

  • The keys are nearly the same as in tui. Only moving between panes uses SPC w instead of Ctrl-w. Statistics are only in tui.
  • You can drag a Gantt bar to change its dates. Everything else in the tracker is read only.
  • If the port is already in use, pick another with --port. --port 0 picks a free one.
  • Press Ctrl-C to stop it.

List — milestones and epics as folders

Unfold milestones and epics, or step inside them, to find issues. The description, sub-issues, commits and history of the issue under the cursor show beside it. Open it with SPC g l in both tui and web.

moai tui
127.0.0.1:6624
  • Enter steps into a milestone or an epic and Backspace steps back out. l unfolds one level and h folds. Tab unfolds everything below.
  • Press / and type to search titles, tags, bodies and notes as you go. Hidden issues are searched too. In web, archived issues are searched only while the archive is shown with SPC v o.
  • SPC f sets conditions such as status, assignee, tag or milestone. While you type, the values you can pick show above.
  • SPC s sorts by several criteria combined — priority, deadline, last update and more. The sort stays for the next run.
  • When an issue assigned to you changes, it gets a [NEW] mark. r marks it read.

Kanban — a board by status

Issues are laid out as cards by status. Each milestone gets a row of its own, so you can see how each release is coming along. Open it with SPC g b in both tui and web.

moai tui
127.0.0.1:6624
  • The backlog and deferred work have columns of their own. The deferred column is hidden by default; SPC v l shows it.
  • In tui, someone else's card shows its assignee. In web, turn the assignee on with SPC c a.
  • h and l move across columns, j and k move between cards in a column.
  • It shares the cursor, filter and view settings with the list, so you keep your place when you switch between the two.
  • You cannot move cards by hand. The agents change the status as they work.

Gantt — your schedule as bars

A date axis sits beside the list, and every issue shows the span you planned and the span actually worked as bars. Open it with SPC g g in both tui and web.

moai tui
127.0.0.1:6624
  • The faint bar runs from the planned start to the deadline, and the coloured bar is the time actually worked. The part past the deadline shows as red hatching.
  • Epics and milestones gather their members' spans into one hatched bar.
  • Zoom in and out by hour, day, week and month. t brings you back to today, and z fits every bar on one screen.
  • Issues blocking the one under the cursor are joined to it by arrows.
  • Drag a bar with the mouse to change its start and deadline. It saves once, when you let go, and if that would pass the deadline of the epic or milestone above, it does not save and tells you why.

Statistics — flow and time taken

See the state of the project's work as bar charts and numbers. Open it with SPC g s in tui. It is not in web.

moai tui
  • Shows the work created and the work finished each week side by side. b switches between weeks and days.
  • See how many issues stand in each status and each priority.
  • Shows the median and p90 of the time from creation to done, and from the start of work to done. Work whose start is unknown is not counted as zero; it is counted separately.
  • Counts the work per AI model, from the model names recorded on the issues.
  • With a filter set, it counts only the issues that match.

Wiki — the repository's manual

Read the repository's markdown documents on screen. Open it with SPC g w in both tui and web.

moai tui
127.0.0.1:6624
  • The list of pages is on one side and the selected page on the other.
  • / searches titles and bodies. The pages that match your words best come first.
  • Pick a link on the page with Tab and open it with Enter. Backspace takes you back to the line you were reading.
  • An issue's detail also shows, below its commits, the wiki pages about that issue and the related sections.
  • The wiki is read only. The pages are files in the repository; the agents edit and commit them when they finish a piece of work.

Directing development with moai

Split big work into milestones and epics

moai groups issues into epics and milestones.

  • Epic — a bundle of issues serving one purpose. When a request touches several files, the agent first shows you a plan split into one epic and three to seven issues, and creates it in one go once you approve.
  • Milestone — what ships together in one release. Attach an epic to a milestone and the issues under it come along.

You never move an epic or a milestone yourself. Start any member and it becomes in progress; finish them all and it becomes done, automatically.

While a milestone is running, the work inside it comes first. moai ready hands out only the running milestone's work and p0 (urgent), and leaves the rest for later. Whether to add work to a running milestone is your decision.

When the agent shows a plan, it also asks for a deadline. With no answer, there is no deadline.

How worktrees are made and merged

When several sessions pile commits onto one branch, they end up waiting on each other to merge. So moai's agents make a separate branch for each piece of work.

  1. Pick up the work. The issue moves to in_progress (moai mv <id> in_progress --from todo). If another session already took it, nothing moves and the agent goes on to the next one.
  2. Make a worktree. A new branch is checked out at .worktrees/<epic> inside the repository. Claude Code, Codex and Antigravity all use the same place.
  3. Work and commit there. With the issue id in the commit subject, moai show <id> finds and shows that issue's commits.
  4. Get it reviewed. When the epic is finished, the whole epic is reviewed once and the review's findings are taken in.
  5. Merge and clean up. It is merged into the base branch with --no-ff, the worktree and branch are removed, and the issue moves to done.
  • The tracker always stays in the root. Run moai inside a worktree and it still reads and writes the root's .moai/. Other sessions see who took what right away, and the tracker file never conflicts on a merge.
  • Work in a milestone starts from the milestone branch. Epic branches are made from milestone/<milestone id> and merged back into it when done. The milestone branch goes into the base branch in one go at the release.
  • moai ready --worktree shows what the neighbouring worktrees are doing.

Backlog

What is not for now goes into the backlog.

moai backlog add 'what if the board could fold by epic'
moai backlog ls
moai backlog
  • A backlog item is an idea not yet settled as work. It does not show on the board or in moai ready.
  • When an idea that comes up mid-work falls outside the current scope, leave it in the backlog.
  • When its time comes, moai backlog promote <id> turns it into an epic and issues. The original backlog item closes, and the new work's history leads back to the old note.
  • Work already created that you have decided not to do right now is deferred, not sent to the backlog: moai defer <id> -m 'why'. --undo brings it back exactly as it was.

Examples

You direct agents in plain words. You can ask like this.

Tidying the backlog

Tidy up the backlog. Merge what overlaps, close what is already done, and prioritize what is worth doing now.

Hand the piled-up backlog to the idle sessions.

The second one calls the supervisor (/moai-supervise). See The supervisor and workers below.

Plan with Fable, in detail

Plan this work with Claude Fable, and write the descriptions in detail so other agents can pick them up right away.

If the plan writes into each issue what is done and why, how far it goes and which files change, another agent can understand the context and carry the work on.

Different models for development and review

In each worker session, use subagents — develop with Sonnet 5.5 at medium, and review with Opus 5.5 at high.

To avoid saying this every time, write the model for each role into your user config. The supervisor reads it every time it hands out work. moai models shows the current values.

[models]
plan    = "fable"    # planning
develop = "sonnet"   # development — most work
complex = "opus"     # the write path, concurrency, work across several files
review  = "opus"     # the epic-end review
review_grade = "high"
effort       = "medium"

Supported environments

Where the supervisor can see and work the workers' windows, you can leave managing the sessions to it as well. Turn on the optional skill for your environment (the optional-skill rows of moai init, or moai skill install --with <skill>).

  • tmux — moai-tmux. The supervisor labels the worker panes, clears a reported pane with /clear, and pastes in a message that did not arrive. When workers run short, it asks before opening new panes.
  • cmux — moai-cmux (cmux 0.65.0 or later). The same as tmux, on cmux tabs.
  • Saycode — moai-saycode. Inside a Saycode session, the supervisor sees the worker sessions through happy agent, sends them work and opens new sessions.

In every environment, the supervisor never closes your panes, tabs or sessions, and leaves an input box alone when someone has typed in it.

Hooks

After moai skill install (or the hooks and skills row of moai init), moai's hooks run at key moments of an agent session.

WhenWhat happens
The session startsA baseline of the warnings is written. After the context is compacted, the work in progress is told again
The first promptThe moai status board is read in once
Before a tool runsThe five rules below are checked
The turn endsIf work in progress is left, the agent is asked to leave a Next: note for the next session

The five rules the hooks keep:

  1. New issues are created inside the work in hand. Anything out of scope goes to the backlog.
  2. Pick up work before changing the repository.
  3. A review is recorded as an issue too. It says what is being looked at and what was taken in.
  4. Never kill your tmux server.
  5. Check first before taking over another agent's work.

A refusal hands over the command that gets through, so the agent fixes it right away instead of waiting on a person (only rule 5 asks one). The hooks never fail the session, and a moai a person types in a terminal does not go through them.

The supervisor and workers

Call /moai-supervise in one Claude Code session and that session becomes the supervisor. Keep one supervisor per repository.

tmux · moai tui · Claude Code · Codex · Antigravity
  1. The supervisor picks backlog items that do not collide. It asks for a deadline where there is none.
  2. It picks the role that fits the work's difficulty (development, complex work, docs, chores) and raises a worker on that role's model. By default the worker is a subagent inside the supervisor's session.
  3. The worker turns the backlog item into an epic, works in a worktree, and reports once review, merge and clean-up are done.
  4. The supervisor checks that the merge happened, the epic closed and the worktree is gone, then sends the next item.
  • To watch the workers' windows yourself, use session workers instead of subagents. Open a few Claude Code sessions in the repository's root, and the supervisor sends work to the idle ones.
  • When a design decision is needed, the worker stops and the supervisor asks you. If you tell the supervisor you are stepping away, workers decide by their recommendation and leave the reason on the issue.
  • The supervisor picks and assigns work and checks the results. Changing code and merging are the workers' job.
